Principles

Two ideas shape every skill here. Knowing them makes the rest of the page predictable.

Test-driven development

Test-driven development, TDD for short, means you write the test before the code it tests. The test fails at first, because the code doesn't exist yet. Then you write code until it passes, then you tidy up. The loop is called red, green, refactor. Red and green are the colours a test runner shows for failing and passing tests.

Red. architect-ticket writes the tests and checks that every one fails for the right reason. Done is now decided, before any real code exists.

Green. implement-ticket writes code until those tests pass. It may not edit the tests, so it can't make the work easier by lowering the bar.

Refactor. refactor-ticket improves the code's shape without changing what it does. The tests prove nothing broke.

Textbook TDD goes around this loop every few minutes, one test at a time. We go around once per ticket, with all its tests at once, and each step is its own skill, its own session and its own commit. It's slower per lap, but each commit is a clean checkpoint you can review on its own. autopilot-ticket runs the same loop in one session for small tickets.

Who decides what

Decisions belong to people. Typing belongs to Claude. The skills that settle what to build and what the code looks like from outside need you in the chat. The ones that only carry out a settled plan run on their own.

implement-ticket, refactor-ticket and autopilot-ticket don't ask for permission, but they don't guess either. They come back to you when:
  • a test contradicts the ticket, or a stub can't do what its docstring promises
  • the same test fails the same way two passes in a row
  • a PCR or ADR blocks the only workable fix
  • a test turns out weaker than the ticket asked for (refactor asks before strengthening it)
  • they finish, with a short report of what they did and the commit hash

Context management

Context window = everything one session holds. Chat, files read, command output. Counted in tokens, about ¾ of a word each. Fuller window, worse Claude. Past ~150k it drops early answers, rereads files, misses bugs in the diff. That's the dumb zone. Rule: finish the job before 150k, then clear. Hence one station per session, handoff through the ticket or the commit, never through memory.

claude
> looks good, commit
⏺

Committed a1b2c3d Architect #42: Keep users logged in across reloads.
Branch 42-fix-expired-session. Tests 5 written, 5 red.

> /context
⏺

118k tokens used

> /clear
⏺

(no content)

> /implement-ticket
⏺

Reading #42 and git diff main...HEAD. 5 acceptance tests red, starting pass 1.

/context shows the count. /clear empties the window, the branch keeps the work. Station heading past 150k? Ticket too big. Stop, split it.

Clear vs compact

/clear empties the window. Back to start-up, nothing else. /compact swaps the chat for a summary Claude writes itself, then keeps going. Smaller, not cleaner. Claude picks what survives, you don't see it, and every instruction after gets read through it. Auto-compact does the same when the window fills. Between stations, always clear. The ticket and the branch hold everything the next station needs.

Three compacts in, this is what sits in front of /implement-ticket:

context after 3 compacts

[summary 1] Worked on #41 password reset. User said no new files, put helpers in auth.py.

[summary 2] Login page CSS misaligned on mobile, tried three fixes, reverted. test_session_expiry is flaky, skipped it.

[summary 3] #42 architect done. Renamed refresh_session to renew_session. 5 tests red.

> /implement-ticket
⏺

Putting the helper in auth.py, no new files. Skipping test_session_expiry as flaky...

  • Unrelated. "No new files" was a rule for #41. Now it shapes #42.
  • Wrong. The "flaky" test was the bug #42 exists to fix. The summary kept the guess, dropped the evidence.
  • Stale. You reversed the rename before committing. The summary was written first, so the code says refresh_session and Claude says renew_session.

After /clear, /implement-ticket reads the ticket and git diff main...HEAD. Both are facts. A summary is Claude's memory of facts.

Repo layout

Skills look in fixed places. Info in the wrong place = info Claude never reads. Keep the project like this:

your-project/
├── CLAUDE.md             commands, loaded every session
├── README.md             how to run the project
├── CONTEXT.md            project vocabulary
├── docs/
│   ├── adr/              decisions, one part of code
│   │   ├── 0001-handlers-depend-inward.md
│   │   └── 0002-no-orm-in-domain.md
│   └── pcr/              conventions, whole project
│       ├── 0001-pytest-for-all-tests.md
│       └── 0002-http-only-through-client.md
├── src/
└── tests/
    ├── test_session.py   module tests, permanent
    └── test_acceptance.py  one ticket, its branch only

No plan files, no TODO.md. Project state lives in GitHub issues: epics, tickets, the decision log in each epic. Done = closed.

Records share one format: Decision, Reason, Consequence, Date, file named NNNN-slug.md. A record blocks the work? The skill names it and stops. It never codes around it.

Setup

The setup sheet has the full steps. The short version, inside Claude Code:

/plugin marketplace add Maxastrand04/Custom-skills
/plugin install max@custom-skills

Restart Claude Code or run /reload-plugins. Every skill from the plugin carries a max: prefix, so /map-epic on this page means /max:map-epic for you. To update later, run /plugin marketplace update custom-skills.

Want the skills without the prefix, or using Antigravity? Clone the repo somewhere you'll keep it and run ./install.sh instead. The README covers that route.

The kanban skills need the gh command line tool, logged in to the repo you work in, because tickets live as GitHub issues.

The board

The skills form a kanban board. Each skill is a station, and a piece of work moves left to right through them. Work starts as a ticket, a GitHub issue filed by either map-epic or new-ticket, never both. From there it takes one of two routes onto a branch. A task ticket goes through the three code stations. An autopilot ticket goes through autopilot-ticket alone.

The git flow

A ticket gets its own branch, cut from main and named <issue-number>-<slug>. Each code station leaves its own commit on that branch, so you can read the history and see exactly what each station did. The three-station route never pushes or merges. Opening the pull request and merging it back is your job.

architect-ticket and autopilot-ticket run git checkout -b from whatever branch you are on. Run git checkout main && git pull before you start either, or the ticket branch will grow out of the wrong place.

Two terms the diagram leans on:

  • Stub. A function with its final name, parameters and docstring, whose body only raises "not implemented". It pins down what the function looks like before anyone writes it.
  • Acceptance file. One test file at the root of the test tree, named in the project's style, like tests/test_acceptance.py or tests/acceptance.test.ts. It holds this ticket's tests and nothing else, and it is the finish line for implement. Refactor moves its tests into the normal test files and deletes it, so main never carries one.

An autopilot branch looks different. It has one Test #42 commit, one Implement #42 commit per behaviour, and a Refactor commit. Then the skill pushes and opens the PR itself. The issue closes when you merge.

What a grilling round looks like

Most skills interview you before they write anything. The questions come in numbered rounds, and every question carries Claude's recommended answer. Here is one round from /new-ticket users can export a report as CSV.

claude
> /new-ticket users can export a report as CSV
⏺

❓ Q1 - Which columns go in the file?: A report table can hide columns the user switched off. Which should the export include?

a) Only the columns visible on screen
b) Every column, hidden ones too
c) A fixed set, the same for every user

➡️ a. The user expects the file to match what they were looking at.

❓ Q2 - Empty report: A filter can leave a report with no rows. What should the user see?

➡️ Disable the export button while the report is empty.

> Q1 a, but always include the row ID. Q2 agree.
⏺

Settled. The export holds the visible columns plus the row ID. Empty reports disable the button.

❓ Q3 - ...

Answer by number and keep it short. Pick an option by its letter, add a tweak if the option is close but not right, or say "agree" to take the recommendation. Disagreeing is fine and often the point. If every answer is "agree", you probably skipped the thinking the interview exists for.

Where to start

map-epic and new-ticket both end in tickets, but they never work on the same thing. map-epic owns every ticket under an epic. new-ticket refuses epic work and points you to map-epic. An epic is a large goal that needs several tickets, and it exists as a GitHub issue titled (N) [epic] ....

Your workUse
Part of a goal that already has an (N) [epic] issue/map-epic N
A goal that needs several tickets and has no epic yet, like "users can import data from CSV"/map-epic plus the goal. It files the epic first
One bug or one small feature that stands alone, like "users get logged out when they reload the page"/new-ticket
Standalone, but too big for one ticket/new-ticket. It offers to split it into sub-issues under a parent ticket
Not sure it's worth doing at all/brainstorming. It ends by naming which of these to run

A quick test: if you can picture three or more tickets that only make sense together, it's an epic. If it ships alone, it's a single ticket.

Once the ticket exists, its label picks the route. map-epic and new-ticket both suggest a label for each task ticket, and you confirm or override it.

LabelRun
task, the default. The ticket adds or changes a function other code calls, touches a PCR or ADR, or can't be undone with one git revert/architect-ticket, then /implement-ticket, then /refactor-ticket
autopilot. Small refactors, bug fixes, and swaps behind a stable interface, where reading the finished diff is cheaper than settling the design first/autopilot-ticket
research or prototype. A question to answer or a mock-up to build before the real ticket can be writtenNo station. Answer it in its own session and close it. The next /map-epic run picks up the answer

map-epic

station 1GitHub only

The only skill that writes epics. Turns a big goal into an epic and splits it into tickets. Run it again later when earlier tickets close, and it turns the vague leftovers into real tickets.

New epic
Interviews you until the goal is one sentence describing what works when the epic is done. Then it files the epic issue, like (3) [epic] CSV import, and offers to move straight on to splitting it.
It does
Asks questions across the whole epic and sorts every item into one of four piles. A task is ready to build. A research ticket is a question someone must answer first. A prototype ticket needs a quick mock-up first. Fog is something you know is coming but can't describe yet, so it stays as a note in the epic. For each task it suggests task or autopilot.
Stops for you
Before filing a new epic issue. Then "Publish this batch?" Then once per task ticket, to review its text and label.
Leaves behind
Sub-issues titled (2.1) [feature] ..., linked to the epic, with "blocked by" links between them. The epic issue gets its notes, decisions and fog filled in.
# new epic
/map-epic users can import their data from a CSV file
# existing epic
/map-epic 2
# later, after some of epic 2's tickets have closed
/map-epic 2
# pick from a list of epics
/map-epic

new-ticket

beside the boardGitHub only

For one piece of work that no epic covers, like a bug or a small feature. If it belongs to an epic, use map-epic instead.

It does
First asks "feature or bug?", then interviews you about what the user sees. It refuses to talk about files, function names or tests. That is architect's job. Before publishing it suggests task or autopilot.
Stops for you
When it suggests splitting into several tickets, and before publishing each one.
Leaves behind
A GitHub issue with Goal, Expected behaviour, Out of scope, and a branch name.
/new-ticket
/new-ticket users get logged out when they reload the page

architect-ticket

station 2red commit

Decides what the code will look like from the outside, then writes failing tests for it. You own this part. Every name and parameter gets agreed with you here.

It does
Reads the ticket and the code around it, posts a "What I found" summary, then interviews you about each new function: name, parameters, return value, and what errors it raises. Then it creates the branch, writes the stubs and the acceptance file, and runs the tests to check every one fails for the right reason.
Stops for you
After "What I found", so you can correct it. Then at the staged diff. Nothing is committed until you approve.
Leaves behind
Branch 42-<slug>, one commit Architect #42: ..., and an ADR in docs/adr/ for each design choice you argued over.
# from an up-to-date main
/architect-ticket 42
# at the diff gate
looks good, commit
# or, to fix something small
rename refresh_session to renew_session, keep the rest

If your objection is about the design itself, not a name, say so. It goes back to the interview rather than patching the code.

implement-ticket

station 3green commit

Writes the code behind the stubs until the acceptance file passes. It may not rename anything or touch a test. Every other choice is its own, so it won't ask you about them.

It does
Reads the ticket and the architect's diff, then loops: write code, run the acceptance file, read failures. It reports each pass as "pass 3: 2 of 6 still red". It runs only the acceptance file, never the whole suite. Old tests the ticket made out of date are refactor's problem.
Stops for you
Only when something is wrong that isn't its call: a test that contradicts the ticket, a stub that can't do the job, or no progress after two passes.
Leaves behind
One commit Implement #42: ... and a comment on the issue listing the passing tests.
# on the ticket branch, in a fresh session
/implement-ticket

refactor-ticket

station 42 or 3 commits

The last station. Checks the tests actually prove what the ticket asked for, runs the full test suite, cleans up the code against the project's records, and closes the issue.

It does
Checks each expected behaviour in the ticket against the tests. Runs the whole suite. An old test the ticket contradicts gets rewritten, and anything else red is a bug implement caused, which it fixes in its own commit. Cleans the code against docs/pcr/, docs/adr/ and its own code standards. Updates CONTEXT.md and README.md if the branch changed something they describe. Moves the acceptance tests into the normal test files.
Stops for you
If a test is weaker than the ticket asked for. It asks before strengthening it.
Leaves behind
Refactor: ... and Tests #42: fold acceptance file, plus Fix #42: ... if implement broke something. The issue is closed.
# on the ticket branch, in a fresh session
/refactor-ticket

After this, push the branch and open a PR into main. That step is yours.

autopilot-ticket

instead of stations 2 to 4opens a PR

For a ticket labelled autopilot. Runs red, green and refactor in one session with no gates, then opens a PR. The review moves from the design, before the code, to the PR, after it.

It does
Reads the ticket and the code it touches, then checks the label still holds. Turns each Expected behaviour line into one failing test, makes them pass one behaviour at a time, runs the existing tests near the files it changed, and cleans up against the same records as refactor.
Stops for you
If the ticket turns out to need a decision: a public function changes, a PCR or ADR is in the way, or a behaviour can't be tested. It names the reason and tells you to relabel and run /architect-ticket. Same escalations as implement otherwise.
Leaves behind
A pushed branch, one Test #42 commit, one Implement #42 commit per behaviour, a Refactor commit, and a PR that closes the issue on merge.
# from an up-to-date main
/autopilot-ticket 42

The PR body starts with a note that AI wrote it on autopilot. Read the diff before you merge. That's the only review it gets.

Side skills

These aren't stations. Use them whenever you need to think something through.

brainstorming

For a raw idea you aren't sure about. Claude tries hard to kill it, reshapes it every time it breaks, and ends with "killed" or "holds" plus which skill should take it next.

/brainstorming cache search results per user so repeat searches are faster

grilling

The interview engine the other skills use. On its own it stress-tests any plan. It's also the one skill here that starts from plain words, no slash command needed. More on the agent configuration page.

Original by Matt Pocock, from mattpocock/skills.

/grilling my plan for splitting the API into two services
grill me on whether we should drop the cache

pro-con

Weighs two or more options, tags each point by how much it matters, and commits to one.

/pro-con Postgres vs SQLite for the first release

eli5

Explains the thing you just asked about for someone who knows nothing about the field. It invokes talk-to-middleschooler for the wording. Too basic? Say so and it switches to talk-to-highschooler. It lasts for one answer, so type it again for the next.

/eli5 what's a database index

eli10

One level up. It assumes algebra and basic programming and defines every term from the field once. It invokes talk-to-highschooler, and drops to talk-to-middleschooler if you say it's still too hard. One answer at a time, like eli5.

/eli10 how does a B-tree index find a row

challenge-pcr

PCRs are project-wide rules in docs/pcr/, for example "all HTTP calls go through http_client.py". No other skill may change them. When one is in your way, this skill judges whether it should change. The default answer is no.

/challenge-pcr 0006 we need a second HTTP library for streaming uploads

Full example

A small bug, from idea to merged PR. Everything you type is below.

# 1. file the ticket
/new-ticket users get logged out when they reload the page
#    answer the rounds, confirm the label, approve the preview. Ticket #42 is filed.

# 2. red
git checkout main && git pull
/architect-ticket 42
#    answer the rounds, review the diff, say "commit"

# 3. green, in a fresh session
/implement-ticket

# 4. refactor, in a fresh session
/refactor-ticket

# 5. ship
git push -u origin 42-fix-expired-session
gh pr create --base main

If you labelled #42 autopilot in step 1, steps 2 to 5 shrink to this:

git checkout main && git pull
/autopilot-ticket 42
#    read the PR it opens, then merge

Skill sources live in the Custom-skills repo. Change them there, and git pull picks the change up everywhere they're installed.
