# ADR-0010: Release decisions live in scripts/release.py

**Decision:** The release workflow MUST take every release decision, meaning the next version, the release notes, and the manifest edits, from `scripts/release.py`, and every decision about publishing the Antigravity tree, meaning whether to publish, which files to replace, and the commit and tag it pushes, from `scripts/build-agy.py publish`. Its YAML MUST only run git, `gh`, those two scripts, and build scripts that build and check a package without deciding anything about the release, such as `scripts/build-codex.py` and `scripts/build-agy.py build` and `check`. The YAML decides nothing itself.

**Reason:** The alternative was the whole release in workflow YAML and inline bash, which is shorter but leaves the version rules where no test can reach them. A stdlib-only script, shaped like `scripts/build-codex.py`, lets `unittest` check the rules against plain lists of commit messages without a repository or GitHub. The Antigravity publish sits in `scripts/build-agy.py` rather than `scripts/release.py`, because its rules are about the Custom-skills-agy repo's layout, which build-agy.py already owns, and not about picking this repo's version. It runs its own git, clone through push, against a remote it is given, rather than leaving the git to the YAML, so tests can point it at a local bare repo and cover the skip, the sync, and the failure paths.

**Consequence:** A change to how versions are picked or notes are grouped is a change to `scripts/release.py` and its tests, never to `.github/workflows/release.yml`. A change to what reaches Custom-skills-agy, or when, is a change to `scripts/build-agy.py` and its tests. The YAML keeps what tests can't cover: the branch check, the push, moving the marker, loading the deploy key, the order of the steps, and the release page. Those stay manual checks. Both scripts MUST stay runnable on the Python version the workflows set up, with no packages to install.
